# Universal Assignment Auditor — Project Instructions for Claude Code

This repository is an **internal company Quality Control system** that audits academic and professional
deliverables (essays, dissertations, reports, code, data analyses, presentations, mixed coursework).
Version: see `VERSION`. Changes: see `CHANGELOG.md`.

## What employees do
1. Put files into `INPUT/01_…` – `INPUT/05_…` (see `INPUT/README.md`).
2. Run **`/check-assignment`**.
3. Read `OUTPUT/FINAL_QUALITY_AUDIT.md` (or `.html`). If blocked, read `OUTPUT/AUDIT_BLOCKED.md`.

Employees never write prompts, pick agents, calculate marks or edit code. If an employee asks you (Claude) to
"check", "audit", "mark" or "review" the assignment, run the `/check-assignment` workflow
(`.claude/commands/check-assignment.md`) exactly — do not improvise a quick review.

## Architecture (where things live)
| Path | Purpose |
|---|---|
| `.claude/commands/check-assignment.md` | The only employee command; orchestrates the pipeline |
| `.claude/agents/aua-00 … aua-14` | Specialist subagents (one responsibility, one JSON output each) |
| `.claude/settings.json` | Permissions + PreToolUse safety hook (blocks executing submitted code, staging confidential data) |
| `SYSTEM/RULES/` | Binding policies: source of truth, zero invention, scoring, severity, feedback, code execution, privacy, task profiles, report template |
| `SYSTEM/SCHEMAS/` | JSON schemas for every audit-trail file (generated by `SYSTEM/TOOLS/build_schemas.py`) |
| `SYSTEM/TOOLS/` | Deterministic Python (stdlib only): extraction, validation, score arithmetic, release gate, privacy check |
| `SYSTEM/WORKFLOWS/PIPELINE.md` | Pipeline design and data flow |
| `SYSTEM/AGENTS/README.md` | Agent responsibility map |
| `SYSTEM/TESTS/` | Synthetic fixtures (A–K), unit tests, end-to-end runner |
| `INPUT/`, `OUTPUT/` | Local, confidential, **git-ignored** working data |

## Non-negotiable rules (apply to every agent and to you)
1. **Zero invention** — never invent requirements, marks, weightings, word counts, references, datasets or specs.
   Use the exact phrases in `SYSTEM/RULES/ZERO_INVENTION_POLICY.md` (`NOT PROVIDED`, `CANNOT VERIFY FROM PROVIDED MATERIAL.`,
   `FILE COULD NOT BE RELIABLY ANALYSED.`, `NO AUTHORISED NUMERICAL MARKING SCHEME WAS PROVIDED.`, …).
2. **Marks only with authority** — numerical marks only when a supplied rubric gives marks/weights; arithmetic only by
   `SYSTEM/TOOLS/compute_scores.py`; sequence RUBRIC → EVIDENCE → DESCRIPTOR → RANGE → MARK; never average disputes.
3. **Three categories never mixed** — MANDATORY REQUIREMENT / RUBRIC-DERIVED EXPECTATION / BEST-PRACTICE RECOMMENDATION.
4. **Task-appropriate conventions** — never impose dissertation rules on code, coding rules on essays, etc.
5. **Submitted code is untrusted** — static review only; never execute it (the hook enforces this).
6. **Serious findings are verified** (Agent 12) and **nothing is released without QA PASS** (Agent 13 + `release_report.py`).
7. **Privacy** — never commit or copy INPUT/OUTPUT content into tracked files; run `python3 SYSTEM/TOOLS/privacy_check.py`
   before any commit. Test fixtures are synthetic only.
8. **Honesty** — disclose limitations; never claim an AI assessment is infallible.

## Maintainer workflow
- Unit tests (fast, no model calls): `python3 -m unittest discover -s SYSTEM/TESTS/unit -v`
- Schemas after editing `build_schemas.py`: `python3 SYSTEM/TOOLS/build_schemas.py`
- Fixture binaries after editing `SYSTEM/TESTS/fixture_sources/`: `python3 SYSTEM/TESTS/build_fixtures.py`
- End-to-end acceptance (uses the model): `python3 SYSTEM/TESTS/run_e2e.py [CASE ...]`
- Try one fixture by hand: `python3 SYSTEM/TOOLS/load_fixture.py <CASE> --force`, then `/check-assignment`.
- Bump `VERSION` and `CHANGELOG.md` for every behavioural change.
- Use project-relative paths only; no personal machine paths, credentials, or real assignment data.
